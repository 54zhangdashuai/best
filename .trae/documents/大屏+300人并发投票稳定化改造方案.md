## 目标与验收
- 大屏页 `/leaderboard` 持续刷新不掉线；允许 ≤1s 的榜单最终一致延迟。
- 300 人同时打开 `/vote` 且集中投票时：`/api/programs`、`/api/config` 不出现大面积 5xx；`POST /api/vote` 成功率 ≥99%，爆发期允许排队但 p95 尽量 <1–2s。

## 现状瓶颈定位（基于当前实现）
- 前端 `Layout` 在所有页面上每 1 秒调用一次 `api.getPrograms()`（即 `GET /api/programs`），导致 300 人=300 req/s 的“全量节目+配置”读压；同时大屏页额外每 2 秒再拉一次同接口。
- `GET /api/programs` 每次都会查询 programs + settings 两张表并组装响应，成为读热点；投票爆发时 SQLite 写锁排队会进一步放大读失败。

## 改造总策略（读写分离 + 缓存吸收读压 + 写入缩短锁占用）
### 1) Nginx：对高频读接口做微缓存（micro-cache）
- 修改 [nginx.conf](file:///d:/project/best/nginx.conf)
  - 增加 `proxy_cache_path`、`proxy_cache_lock`，给 `/api/programs`、新加的 `/api/config` 启用 0.5–1s 微缓存。
  - 启用 `proxy_cache_use_stale ...`，上游短暂抖动时返回旧缓存，避免前端看到 5xx。
  - 为 `POST /api/vote` 增加限流/突发（考虑 NAT，设置较高 burst），并调大 `proxy_read_timeout` 防止写入排队被网关 504。
  - 增加可观测 header（如 `X-Cache`）和关键日志字段（upstream_status/response_time）。

### 2) 后端：拆分轻量配置接口 + 内存短缓存
- 修改 [backend/src/server.ts](file:///d:/project/best/backend/src/server.ts)
  - 新增 `GET /api/config`（仅返回 config/remaining_seconds），供倒计时 UI 使用。
  - 为 `GET /api/programs` 与 `GET /api/config` 增加进程内 TTL 缓存（例如 200–500ms），即使绕过 Nginx 也能显著减轻 SQLite 压力。
  - 将 settings 读取逻辑抽成函数并复用，减少重复解析。
- 修改 [backend/src/db.ts](file:///d:/project/best/backend/src/db.ts)
  - 保持现有 WAL/busy_timeout；如需要再提高 `busy_timeout`（例如 10s）以覆盖投票爆发窗口。

### 3) 后端：缩短投票事务时间（降低写锁占用）
- 修改 [backend/src/server.ts](file:///d:/project/best/backend/src/server.ts)
  - 在事务中把 “多次 UPDATE programs” 合并成单条 `UPDATE programs SET vote_count = vote_count + 1 WHERE id IN (...)`，减少 SQL 次数与锁持有时间。
  - 继续用 `vote_sessions(client_ip PRIMARY KEY)` 做原子防重复（已具备并发正确性）。

### 4) 前端：把 1s 倒计时轮询从“全量 programs”切到“config-only”
- 修改 [client.ts](file:///d:/project/best/client.ts)
  - 新增 `api.getConfig()` 调用 `/api/config`。
- 修改 [App.tsx](file:///d:/project/best/App.tsx)
  - `Layout` 的 1s 轮询改为 `getConfig()`，不再每秒拉取完整节目榜单。
  - 大屏页继续每 2s 拉榜单（或保持 2s + 失败退避）；必要时可让大屏也读更轻的 `/api/leaderboard`（可选项）。
  - 增加简单退避：连续失败后轮询间隔 2s→4s→8s，恢复成功后回到默认频率。

### 5) 压测脚本对齐真实行为并回归验证
- 更新/新增 tests/load 下的 k6 脚本：
  - 300 VU 主要压 `/api/config`（1s）+ `/api/programs`（2s）+ 投票爆发 300（同一时间窗口）
  - 验证：5xx 比例、p95 延迟、投票成功率、爆发阶段是否仍出现大量 5xx。
