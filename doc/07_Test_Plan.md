## 4. 性能与并发压测 (Load & Stress Testing)

### 4.1 验收目标（300 人场景）
*   **大屏页**：打开 `/leaderboard` 能稳定展示，刷新不中断（允许 ≤1s 的数据延迟）。
*   **投票页**：300 人同时访问 `/vote`，同一时间窗口集中投票，系统不出现大面积 5xx。
*   **投票正确性**：每个 `clientId` 只能成功投票一次；并发双击/重试不应导致重复记票。

建议指标（上线前至少满足）：
*   `GET /api/programs`：5xx 率 < 0.5%，p95 < 200ms（启用网关缓存后更容易达标）。
*   `POST /api/vote`：成功率 ≥ 99%，p95 < 1s（峰值阶段允许短暂升高，但不应持续 > 2s）。

### 4.2 压测场景与脚本
压测建议使用 k6；仓库已提供对应脚本（见 `tests/load/`）。

*   **场景 A：只压读（榜单轮询）**
    *   目标：验证 `/api/programs` 在 300 人高频轮询下的稳定性，并为缓存/限流调优提供依据。
    *   脚本：`tests/load/k6_strict_300users.js`
    *   建议参数：`VUS=300, POLL_INTERVAL_SECONDS=0.5, SOAK=60s`（严苛模式）

*   **场景 B：只压写（集中投票爆发）**
    *   目标：验证 `POST /api/vote` 在 300 人同一时间窗口提交时的成功率与延迟。
    *   脚本：`tests/load/k6_burst_poll_vote_300users.js`（仅启用 vote_burst 场景亦可）

*   **场景 C：读写并行（最坏情况，推荐作为上线门槛）**
    *   目标：同时模拟 300 人轮询 + 300 人集中投票，验证系统在最坏情况下的 5xx、超时与投票延迟。
    *   脚本：`tests/load/k6_burst_poll_vote_300users.js`

### 4.3 结果判读要点
*   **如果 `GET /api/programs` 出现明显 5xx**：优先启用/调大网关微缓存 TTL（0.5~1s）与 `stale-if-error`；其次降低前端轮询频率（2s 起）。
*   **如果 `POST /api/vote` p95 延迟显著升高**：说明写锁等待/排队明显；需要评估投票峰值窗口（倒计时最后 5~10 秒）并增加投票请求保护（限流、重试策略与明确的错误码）。
*   **如果投票成功率下降**：检查后端是否出现 `SQLITE_BUSY` 类错误，以及网关是否存在连接/超时限制导致 499/504 等。
